# Health Assistant — техническое задание (MVP)

## 1. Описание проекта

**Health Assistant** (далее — «Агент») — умный ассистент для анализа здоровья, физических нагрузок и тренировок. Работает оффлайн (без выхода в интернет из контейнера Агента). Общение с пользователем — на русском языке; архитектура должна быть готова к мультиязычности.

Агент — это сервис, запущенный в Docker на отдельном сервере. Снаружи он выглядит как набор HTTP API, к которому подключаются:
- админка,
- тестовый чат пользователя,
- внешние сервисы (мобильное приложение через webhook'и алертов, источники пользовательских данных).

Рядом, **вне** docker-compose этого проекта (на той же машине или соседней, развёрнуто отдельно), работают:
- **LLM-бэкенд**: Ollama (dev/отладка) или vLLM (продакшн). Размер основной модели ~8B.
- **Эмбеддинги**: Ollama `/api/embeddings` (dev) или TEI / Infinity (prod). Модель — `nomic-embed-text-v2-moe`.

Поднятие и поддержка этих бэкендов — **не входит в задачи проекта**. Агент общается с ними по сети через единый интерфейс `LLMClient` и `EmbeddingsClient`. Приоритетный протокол — **OpenAI-совместимый** (`/v1/chat/completions`, `/v1/embeddings`): vLLM, TEI, Infinity и многие другие его поддерживают, и это позволяет иметь одну реализацию клиента на всех. Ollama имеет свой нативный API (`/api/chat`, `/api/embeddings`); при необходимости — отдельная реализация под Ollama. Никаких прямых обращений к Ollama/vLLM из бизнес-кода — только через интерфейс. Подробнее про сетевую связность — см. раздел 19.3.

**Целевая нагрузка продакшна** — 100+ одновременных пользователей. На MVP цель — функциональная корректность и стабильность под 5–10 одновременных. Нагрузочное тестирование и оптимизация — отдельная фаза после MVP.

### 1.1. Публичные API и авторизация

Агент предоставляет три группы API под разными префиксами:

| Префикс | Назначение | Авторизация на MVP |
|---|---|---|
| `/api/chat/...` | Боевой чат (для мобильного приложения и партнёров) | API-key или JWT в заголовке `Authorization` |
| `/admin/api/...` | Админка | Basic Auth (логин/пароль из `.env`) |
| `/testchat/api/...` | Тестовый чат для разработки | Basic Auth, в проде — отключён или закрыт сетью |

`/api/chat/...` доступен извне; `/admin/api/...` и `/testchat/api/...` в prod проксируются только из доверенной сети (через reverse-proxy, см. раздел 19).

Авторизация боевого чата на MVP — простой механизм (заранее выданный API-key на пользователя или JWT с подписью), без OAuth/сессий. Подмена `user_id` в запросах **не должна быть возможна**: identity берётся из токена, не из тела запроса.

Все API-контракты (request/response модели) описываются через Pydantic v2 → FastAPI автогенерирует OpenAPI-схему по `/api/openapi.json`. Это и есть документация API; вольных интерпретаций контрактов нет.

## 2. Технологический стек

- **Язык**: Python 3.11+
- **Web framework**: FastAPI (async)
- **БД**: PostgreSQL 16+ с расширением **pgvector** (всё в одном Postgres — и реляционные данные, и векторы)
- **Сессии диалога (горячее хранилище)**: Redis. Используется только под сессии и rolling summary. Очереди и кэш на MVP не вводим — добавим осознанно, когда профайлинг покажет необходимость.
- **Фоновые задачи / планировщик**: APScheduler с job store в Postgres (для MVP достаточно; Celery + Redis — позже, если появятся реальные очереди)
- **Стриминг в чат**: **SSE** (Server-Sent Events)
- **Схемы Tools и валидация**: Pydantic v2
- **Контейнеризация**: Docker + docker-compose
- **Тесты**: pytest, pytest-asyncio
- **Миграции**: Alembic

Один репозиторий, два docker-compose пресета (dev / prod) — см. раздел 19. Админка и тестовый чат — часть проекта Агента (бэкенд под общим API, фронт может быть отдельным SPA в том же репо).

## 3. Архитектура и структура репозитория

Примерная структура (детали — на усмотрение разработчика, но разделение по слоям обязательно):

```
/app
  /api              # FastAPI роутеры (chat, admin, alerts, health)
  /pipeline         # Context Builder, Intent, Router, Planner, Response Generator
  /tools            # Реестр инструментов и их реализации
  /rag              # Индексация, retrieval, чанкинг
  /llm              # LLMClient, EmbeddingsClient + реализации

  /alerts           # Proactive monitoring + правила
  /safety           # Классификатор и blocked-ветка
  /i18n             # Системные промпты и шаблоны по локалям
  /admin            # API для админки
  /testchat         # API для тестового чата
  /generators       # Генератор тестовых данных
```

## 4. Pipeline обработки запроса

```
User Query
  → Context Builder
  → Intent Detection
  → Router  (blocked | fast_direct | tool_simple | template_plan | planner)
  → Response Generator
  → Response Delivery (stage events + token streaming через SSE)
```

### 4.1. Context Builder
Собирает на вход pipeline:
- последние **N=10** пар сообщений (user + assistant) полностью,
- **rolling summary** более старых сообщений (генерируется отдельным вызовом LLM при превышении порога),
- ключевые факты из профиля пользователя (язык, role, age, gender, sports, units),
- временной контекст (текущее локальное время и дата пользователя по `timezoneOffset`),
- активный `pending_clarification` из сессии, если он есть (см. раздел 9) — это сигнал pipeline, что текущее сообщение продолжает предыдущий запрос.

TTL сессии — 24 часа бездействия, потом сессия закрывается, новый запрос открывает новую.

### 4.2. Intent Detection
Классификация запроса в одну из категорий: `blocked`, `smalltalk`, `product_help`, `knowledge_query`, `data_query_simple`, `data_query_complex`, `template`, `recommendation`, `other`. Реализация — отдельный LLM-вызов с guided decoding (vLLM) или `format=json` + ручная валидация (Ollama). Промпт короткий, выход — структурированный JSON `{intent, confidence, args?}`.

Семантика категорий:
- `blocked` — опасные темы (медицина, лекарства), см. раздел 11.
- `smalltalk` — приветствия, отвлечённый разговор.
- `product_help` — справка по продукту («Как добавить тренировку»), идёт через `product_faq`.
- `knowledge_query` — справочные вопросы по домену («Что такое HRV?», «Сколько белка нужно?»), идёт через RAG (`search_knowledge`) в ветке `tool_simple`.
- `data_query_simple` — конкретный вопрос по данным с одним tool («Сколько шагов сегодня»).
- `data_query_complex` — сложный вопрос по данным, требующий нескольких tools или планирования.
- `template` — попадает в `template_plan`. В `args.template_id` intent classifier указывает конкретный шаблон («morning_analysis», «weekly_summary»); роутер по `template_id` находит план в реестре.
- `recommendation` — запрос рекомендаций или плана тренировок (RAG + данные пользователя).
- `other` — что-то ещё, идёт в `planner`.

**Ответ на ранее заданный уточняющий вопрос — не отдельный intent**, а контекст. Если в сессии есть активный `pending_clarification` (см. раздел 9), Context Builder подмешивает `original_intent` и `original_query` во вход pipeline. Intent detection в этом случае пропускается (или используется только для проверки, что пользователь не сменил тему); pipeline идёт по ветке роутера, соответствующей `original_intent`, с обогащённым контекстом.

### 4.3. Router
Критерии веток (проверяются в этом порядке):

| Ветка | Условие | Какие intent'ы попадают | Что делает |
|---|---|---|---|
| `blocked` | safety-классификатор сработал, либо intent=blocked | `blocked` | Возвращает безопасный отказ из шаблона |
| `fast_direct` | intent ∈ {smalltalk}, низкая сложность | `smalltalk` | Один LLM-вызов с минимальным контекстом |
| `tool_simple` | intent уверенно (`confidence >= порога`) маппится на ровно 1 tool, все обязательные аргументы извлечены | `data_query_simple`, `knowledge_query`, `product_help` | Вызов одного tool → Response Generator |
| `template_plan` | intent=`template`, `args.template_id` найден в реестре шаблонов | `template` | Выполняется заранее заданная последовательность tool-вызовов, без участия planner |
| `planner` | всё остальное | `data_query_complex`, `recommendation`, `other`, а также любой intent с низким confidence | Loop: tool retrieval (top-3..5) → LLM выбирает tools → выполнение → проверка достаточности данных → ответ или уточняющий вопрос |

### 4.4. Response Generator
Получает на вход:
- исходный запрос пользователя,
- релевантный контекст диалога,
- результаты tools (уже посчитанные числа и факты),
- результаты RAG (если использовались),
- инструкцию по формату ответа (из i18n-шаблонов).

LLM формулирует естественный ответ. **LLM никогда не считает агрегаты, проценты, средние, рекорды и сравнения сама** — все числа приходят из tools уже посчитанными.

### 4.5. Response Delivery

Стриминг через **SSE**. События идут **последовательно** (не параллельно): сначала стадии и tool-вызовы, потом токены ответа.

**Типы событий**:
```
event: stage  data: {"stage":"intent","status":"start"}
event: stage  data: {"stage":"intent","status":"end","duration_ms":120}
event: tool   data: {"tool":"get_workouts","status":"start","args":{...}}
event: tool   data: {"tool":"get_workouts","status":"end","duration_ms":80,"result_summary":"..."}
event: token  data: {"text":"Сегодня "}
event: token  data: {"text":"ты пробежал "}
event: done   data: {"message_id":"..."}
event: error  data: {"code":"...","message":"..."}
event: cancelled data: {"reason":"user_cancelled"}
```

В `result_summary` для tool — краткое описание (не полный JSON), чтобы UI мог показать «Получил тренировки за неделю». Полные результаты доступны через админку.

**Отмена обработки**:
- Отдельный endpoint `POST /testchat/api/sessions/{session_id}/cancel` (и аналогично для боевого чата).
- Pipeline проверяет флаг отмены **между этапами**: после каждого `stage end`, после каждого `tool end`, перед каждой итерацией planner-а, и перед началом стриминга токенов.
- При срабатывании — отправляется `event: cancelled`, SSE-соединение закрывается, текущее сообщение помечается в БД как отменённое.
- Внутри LLM-вызова отмена не прерывает генерацию (это требует поддержки на уровне бэкенда, не на MVP). Минимально: проверка перед вызовом.

### 4.6. Таймауты, ошибки и SLA

**Таймауты** (значения по умолчанию, переопределяются через раздел «Конфигурация»):
- Глобальный таймаут на запрос пользователя — `60s`.
- Таймаут на один LLM-вызов — `30s`.
- Таймаут на один tool-вызов — `10s`.
- Таймаут на один embeddings-вызов — `5s`.

**Поведение при ошибках**:
- Tool упал → одна повторная попытка только если tool помечен как идемпотентный; иначе planner получает ошибку как сигнал «данных нет», просит у пользователя уточнение или сообщает о невозможности.
- LLM не ответил / превысил таймаут → отправляется `event: error` с code=`llm_timeout`, пользователь видит безопасное сообщение об ошибке из i18n.
- LLM-бэкенд недоступен → fast-fail на уровне `LLMClient` с понятной ошибкой; в админке health-check сразу показывает красный статус.
- Превышен `PLANNER_MAX_ITERATIONS` → planner возвращает уточняющий вопрос либо безопасный ответ «не получилось разобраться, уточните…».

**Целевые SLA на MVP** (не для прода, а как ориентир для разработки):
- `tool_simple` и `template_plan`: p50 ≤ 5с, p95 ≤ 15с до начала стриминга токенов.
- `planner` и `recommendation`: без жёсткого SLA на MVP, но запрос укладывается в глобальный 60с-таймаут.
- Стриминг токенов начинается как только готов первый токен от LLM (без буферизации на стороне Агента).

## 5. Tools

- **Native tool-calling** на стороне LLM.
- **Tool retrieval** перед planner-ом: на каждой итерации planner получает top-3..5 наиболее релевантных tools из реестра (через embeddings по описанию tool + текущий запрос/состояние). Передавать в LLM весь реестр — нельзя.
- **Guided decoding** для vLLM (JSON Schema из Pydantic). Для Ollama — `format="json"` + ручная валидация.
- Реестр tools — декларативный (Python-классы или функции с Pydantic-схемами входа/выхода). Добавление нового tool не должно требовать правок pipeline.

**Принцип**: вся математика, агрегации и сравнения с нормами — внутри tools на Python. LLM получает структурированный результат.

Минимальный набор tools на MVP (примерный):
- `get_user_profile`
- `get_workouts(period, sport_type?, aggregation: detailed|summary)`
- `get_daily_metrics(date | range, metrics?)`
- `get_metric_stats(metric, period, stat: avg|min|max|sum|trend)`
- `compare_to_baseline(metric, period)` — сравнение с личной базой и нормой по профилю
- `get_records(metric|sport_type, scope: all_time|year|month)`
- `search_knowledge(query, collections?: list[str])` — RAG, фильтр по collection (см. раздел 7.2)
- `get_product_help(question)` — справка по продукту (см. п. 7)

## 6. Данные пользователя

Три основные сущности (структура — как в исходном описании, см. Приложение A):
- **Профиль пользователя**
- **Тренировки**
- **Дневные метрики**

Хранение — в Postgres, с индексами по `user_id`, датам, `sport_type`.

**Источник данных**:
- На MVP — **детерминированный (seed-based) генератор** тестовых данных. Должен генерировать несколько профилей-персон: «новичок», «продвинутый», «пересыпает», «перетренирован» — для проверки edge cases. Генератор воспроизводим (один и тот же seed → одни и те же данные).
- В дальнейшем — реальный API. Слой доступа к данным изолирован репозиториями, чтобы переключение источника не задевало pipeline.

Изменение структуры пользовательских данных не должно ломать pipeline: tools принимают и отдают структурированные DTO (Pydantic), маппинг ORM ↔ DTO в одном месте.

## 7. RAG и справочные ответы

### 7.1. Справочные вопросы по продукту
Вопросы вида «Что ты умеешь?», «Как добавить тренировку», «Где посмотреть мой VO2max в приложении» — **не идут через RAG**. Это отдельная таблица `product_faq`:

```
product_faq(id, locale, question_canonical, question_variants[], answer, deeplink?, updated_at)
```

Маршрут: intent=`product_help` → tool `get_product_help` → matching по embeddings + порог сходства → готовый ответ из таблицы (опционально с deeplink в UI). Фоллбэк — короткий универсальный ответ «Я умею…».

Причины такого решения: ответы должны быть стабильными, редактируемыми продактом без перегенерации индекса, без галлюцинаций, набор маленький и обновляется централизованно. RAG поверх большой документации можно подключить как fallback позже.

### 7.2. Знаниевая база (RAG)
Назначение — отвечать на профильные справочные вопросы («Что такое HRV?», «Сколько белка нужно?») и быть источником материалов для рекомендаций и планов тренировок.

**MVP**: 20–40 чанков по 5 категориям (физиология, питание, восстановление, тренировки общая теория, безопасность). Чанки — markdown-файлы в репозитории, индексируются скриптом при старте.

**Структура индекса**:
```
rag_chunks(
  id,
  content TEXT,
  embedding vector(768),       -- размерность под nomic-embed-text-v2-moe
  collection TEXT,             -- 'general' | 'methodology:{id}'
  metadata jsonb,              -- category, source, lang, author/coach_id, и т.п.
  created_at, updated_at
)
```

Поле `collection` обязательно с самого начала — заложено под будущий функционал, когда тренер сможет загрузить методику, а спортсмен в профиле выберет её как руководство. Авторство методики (тренер, который её создал) хранится в `metadata.coach_id`. Retrieval умеет фильтровать по списку collections (например, `['general', 'methodology:42']`).

Атрибуты `category`, `source`, `lang` — внутри `metadata jsonb`, чтобы добавление новых атрибутов не требовало миграции.

На MVP используется только `general`, но код retrieval уже принимает фильтр.

**Смена модели эмбеддингов** требует полной реиндексации (разные модели — разное векторное пространство). На горячую не меняется; в админке при выборе другой embeddings-модели — баннер «потребуется реиндексация».

### 7.3. Чанкинг и embeddings
- Размер чанка ~500 токенов с overlap ~50.
- Эмбеддинги — `nomic-embed-text-v2-moe` через `EmbeddingsClient`.
- Поиск — векторный (cosine) с возможностью добавить keyword (BM25) позже.
- Ре-ранкер — не на MVP, заложить точку расширения.

## 8. Память диалога

- **Краткосрочная**: последние 10 пар (user+assistant) сообщений в полном виде, хранятся в Redis с ключом по session_id, и в Postgres (`messages`) для истории/админки.
- **Долгосрочная в рамках сессии**: rolling summary — генерируется отдельным LLM-вызовом, когда история превышает порог. **Источник правды — Redis**, в `sessions.summary` пишется текущий snapshot при каждом обновлении (для долговременного хранения и доступа из админки). История версий summary не ведётся.
- **Между сессиями**: на MVP — только профиль пользователя. Долгосрочная пользовательская память (предпочтения, цели) — точка расширения, не в MVP.
- **TTL сессии**: 24 часа бездействия. По истечении — Redis-данные испаряются, в Postgres `sessions.closed_at` ставится через фоновую задачу.

## 9. Уточняющие вопросы

Если на этапе planner LLM (или явная проверка) определяет, что данных для ответа не хватает, или запрос неоднозначный, Агент:
1. Возвращает ответ-уточнение пользователю (одним сообщением, без выдуманных чисел).
2. Сохраняет состояние «ожидание уточнения» в сессии (что именно не хватает, какой был исходный intent).
3. На следующее сообщение пользователя Context Builder подмешивает это состояние во вход pipeline; planner или tool_simple учитывают его при достройке запроса.

**Структура состояния** (поле `pending_clarification` в Redis-объекте сессии, рядом с историей):
```
{
  "original_intent": "data_query_complex",
  "original_query": "Покажи мои тренировки",
  "missing_fields": ["period"],
  "asked_at": "2026-04-28T10:15:00Z",
  "asked_message_id": "..."
}
```

Очищается:
- после следующего ответа пользователя (любого — даже если он не уточнил, а сменил тему),
- по таймауту (например, 10 минут — настраиваемый порог),
- при явном сигнале от пользователя «отмена/неважно».

Признак «не хватает данных» — это явный результат tool-вызова или valid состояние planner-а, а не угадывание LLM.

## 10. Шаблонные сценарии

Реестр шаблонов (`template_plan`) — заранее определённые последовательности tool-вызовов под устойчивые запросы:

- `morning_analysis` («Утренний анализ») — recovery, HRV, RHR, сон за прошлую ночь, рекомендация на день.
- `weekly_summary` — тренировки и метрики за неделю, тренды.
- (далее — расширяемо)

Каждый шаблон — декларативное описание шагов (какие tools с какими аргументами, в каком порядке, с какими условиями), без участия LLM в выборе шагов. LLM подключается только в Response Generator.

Добавление нового шаблона — добавление одного файла/записи, без правок pipeline.

## 11. Безопасность

Первая ветка роутера — `blocked`. Срабатывает для:
- медицинских диагнозов и назначений лекарств,
- дозировок препаратов,
- расстройств пищевого поведения (рискованные сценарии),
- темы, явно выходящие за домен и потенциально вредные.

Реализация: лёгкий классификатор (LLM-вызов с короткой инструкцией + чёрный список ключевых паттернов как быстрая преградa перед классификатором). Ответ — из шаблонов (мягкий отказ + рекомендация обратиться к специалисту).

Лёгкий смолток на отвлечённые темы — допустим (`fast_direct`), но Агент не должен надолго уходить от своего профиля.

## 12. Proactive Alerts (фоновый мониторинг)

Заложить каркас на MVP:
- Отдельный модуль `/alerts` с планировщиком (APScheduler).
- Правила алертов — декларативные (например, `hrv_drop`, `rhr_spike`, `inactivity`, `weekly_summary_ready`), используют те же tools, что и чат.
- При срабатывании правила:
  1. Запись в таблицу `alerts(id, user_id, rule, payload, created_at, delivered_at?)`.
  2. POST на внешний webhook (URL из конфига) для оповещения мобильного приложения.
- На MVP — каркас + одно реальное правило (`hrv_drop`) как пример. Остальные — заглушки/декларации.

**Структура правила** (декларативно, базовый класс):
```python
class AlertRule(Protocol):
    code: str                 # 'hrv_drop'
    schedule: str             # 'every 1h' | 'cron: 0 8 * * *'
    enabled_default: bool     # стартовое значение в БД при первой загрузке

    async def check(self, user, tools) -> Optional[AlertPayload]:
        # вернуть payload, если нужно отправить алерт; иначе None
        ...
```

Добавление нового правила = добавление одного файла в `/alerts/rules/`, регистрация в реестре. Engine pickup-ит расписание, читает toggle и пороги из конфига (раздел 15.2.G), гоняет `check` для всех активных пользователей.

**Тексты для пользователя** хранятся в отдельной таблице `alert_descriptions`:
```
alert_descriptions(
  rule_code TEXT,            -- 'hrv_drop'
  locale TEXT,               -- 'ru'
  title TEXT,                -- короткий заголовок для push
  body_template TEXT,        -- шаблон с плейсхолдерами, например '{hrv_value} ниже базы на {drop_pct}%'
  updated_at TIMESTAMPTZ,
  PRIMARY KEY (rule_code, locale)
)
```

Редактируется продактом через раздел «Конфигурация → Алерты» в админке. Правило передаёт `payload` с числами, engine подставляет их в `body_template` для нужной локали и отправляет в webhook.

## 13. Логирование

Структурированное, в Postgres. Не «всё подряд» — конкретный набор таблиц с retention policy.

**Таблицы**:
- `sessions(id, user_id, started_at, last_activity_at, closed_at, summary)`
- `messages(id, session_id, role, content TEXT, metadata jsonb, created_at)` — `content` это итоговый текст; `metadata` под структурированные элементы ответа в будущем (графики, deeplinks), на MVP nullable.
- `pipeline_stages(id, message_id, stage, started_at, ended_at, duration_ms, status, meta jsonb)`
- `llm_calls(id, message_id, stage, model, prompt jsonb, response jsonb, tokens_in, tokens_out, duration_ms, created_at)`
- `tool_calls(id, message_id, tool_name, args jsonb, result jsonb, duration_ms, status, error?, created_at)`
- `rag_queries(id, message_id, query, collection_filter, top_k, results jsonb, duration_ms, created_at)`
- `alerts(id, user_id, rule, payload jsonb, created_at, delivered_at)`

**Retention**:
- Детальные `llm_calls`, `tool_calls`, `rag_queries`, `pipeline_stages` — 30 дней.
- `messages`, `sessions`, `alerts` — без авто-удаления.
- Скрипт периодической очистки + ежедневная агрегированная статистика в отдельную таблицу `daily_stats` (число сессий, среднее время ответа, доли по веткам роутера, ошибки).

**Партиционирование**:
- Таблицы `llm_calls`, `tool_calls`, `rag_queries`, `pipeline_stages` партиционируются по дате (range partition по `created_at`, гранулярность — неделя).
- Очистка по retention реализуется через `DROP PARTITION` старых партиций, а не через `DELETE` — это на порядки дешевле и не приводит к bloat.
- Создание новых партиций — фоновая задача в APScheduler (раз в сутки готовит партиции на следующую неделю вперёд).
- На MVP это можно реализовать через `pg_partman` или вручную через миграции — на усмотрение разработчика.

**Запись логов — асинхронная и батчевая**:
- Логи (`pipeline_stages`, `llm_calls`, `tool_calls`, `rag_queries`) **не пишутся синхронно в горячем пути pipeline**. Иначе на проде с 100+ юзерами это десятки коммитов в секунду на основном пути.
- Реализация: in-memory queue (`asyncio.Queue` или аналог) + фоновый writer-таск, который сбрасывает накопленные записи в БД либо раз в N мс (например, 200), либо при достижении K записей.
- При нештатном падении контейнера небольшая часть последних логов может потеряться — это допустимый компромисс для MVP. Критичные данные (`messages`, `sessions`, `alerts`) пишутся синхронно.

Все «сырые» промпты и ответы LLM хранятся как `jsonb`. Это нужно для дебага и отладки в админке.

## 15. Конфигурация (раздел админки)

### 15.1. Источник правды и применение

- **Главный источник конфига — БД.** `.env` используется только как seed при первом старте: если в БД пусто, значения подтягиваются из `.env` и сохраняются. Дальше `.env` игнорируется до следующего пустого старта.
- **Применение изменений — только после рестарта контейнера.** В UI после сохранения показывается баннер «Изменения вступят в силу после перезапуска» и кнопка «Перезапустить» (если есть техническая возможность; иначе — инструкция). Это сознательное решение: исключаем гонки и неконсистентные состояния pipeline в момент изменения конфига.
- **Версионирование**: каждое сохранение пишет запись в `config_history` (см. ниже). Откат — копированием значений из выбранной версии в активный конфиг (с тем же требованием рестарта).
- **Профили конфигурации (наборы настроек) — не на MVP.** Один активный конфиг.

### 15.2. Что настраивается

**A. Модели**
- Выбор основной LLM из списка доступных у бэкенда. Список подтягивается динамически: для Ollama через `/api/tags`, для vLLM через `/v1/models`. Метаданные (размер, контекст, квантизация) — отображаются если бэкенд их отдаёт.
- Выбор embeddings-модели аналогично, из списка от соответствующего бэкенда.
- Кнопка «проверить» рядом с каждой моделью — отправляет тестовый запрос (короткий prompt / dummy text), показывает latency и статус. Не требует рестарта.

**B. Параметры LLM по этапам pipeline**

Этапы с отдельными пресетами:
- `intent_detection`
- `router_safety` (классификатор blocked-ветки)
- `planner`
- `response_generator`
- `summary_generator` (для rolling summary в памяти диалога)
- `template_response` (Response Generator внутри template_plan)
- `product_help_match` (если используется LLM для матчинга, иначе только embeddings)

Для каждого пресета:
- `temperature`, `top_p`, `top_k`
- `max_tokens`
- `seed` (опционально, для воспроизводимости в дебаге)
- `guided_decoding` (on/off; для Ollama — fallback на `format=json`)
- `system_prompt_id` — выбор из реестра промптов в `/i18n/{locale}/prompts/...`. **Свободный ввод системного промпта в UI запрещён** — это нарушает версионирование, локализацию и контроль изменений. Редактирование текстов промптов — через коммит в репозиторий.
- `model_override` (опционально) — позволяет указать другую модель для конкретного этапа. По умолчанию пусто, используется основная.

**C. Пороги и лимиты pipeline**
- `INTENT_CONFIDENCE_THRESHOLD`
- `RAG_TOP_K`, `RAG_SIMILARITY_THRESHOLD`
- `TOOL_RETRIEVAL_TOP_K`
- `PLANNER_MAX_ITERATIONS`
- `CONTEXT_HISTORY_PAIRS` (по умолчанию 10)
- `SESSION_TTL_HOURS` (по умолчанию 24)
- `LOG_RETENTION_DAYS` (по умолчанию 30)

**D. Управление RAG**
- Список collections с числом чанков в каждой и временем последней индексации.
- Кнопка «переиндексировать» для `general` (асинхронная задача, прогресс отображается).
- Просмотр чанков: список с поиском по тексту и фильтром по collection/category. Просмотр содержимого чанка. Удаление — на MVP вручную.

**E. Управление product_faq**
- CRUD по записям (`question_canonical`, `question_variants[]`, `answer`, `deeplink`, `locale`).
- Эмбеддинги для матчинга пересчитываются автоматически при сохранении записи.
- Тест-инструмент: ввести произвольный вопрос → показать топ-3 совпадения со скорами.

**F. Управление шаблонами (`template_plan`)**
- Просмотр реестра шаблонов и их шагов (read-only).
- Toggle включён/выключен.
- Редактирование шагов — не на MVP (требует deep-структурного UI).

**G. Алерты**
- Список правил с описанием.
- Toggle включён/выключен по каждому.
- Параметры порогов конкретных правил (для `hrv_drop` — % дропа и окно сравнения).
- URL вебхука для отправки алертов в мобильное приложение.
- Тестовая отправка вебхука (с dummy payload).
- CRUD по `alert_descriptions` (заголовок и шаблон тела для push'a) с разбивкой по локалям. Тест-инструмент: ввести dummy payload → показать, как будет выглядеть подставленный текст.

**H. Безопасность**
- Список заблокированных тематик (категории blocked-классификатора) с возможностью включения/выключения.
- Просмотр последних N сработок blocked-ветки (запрос пользователя, причина блокировки, время) — для аудита и калибровки порогов.

### 15.3. Структура хранения в БД

```
config_active(
  key TEXT PRIMARY KEY,        -- например, 'llm.intent_detection.temperature'
  value JSONB NOT NULL,
  updated_at TIMESTAMPTZ,
  updated_by TEXT              -- логин админа
)

config_history(
  id BIGSERIAL PRIMARY KEY,
  changed_at TIMESTAMPTZ NOT NULL,
  changed_by TEXT NOT NULL,
  changes JSONB NOT NULL,      -- [{key, old_value, new_value}, ...]
  comment TEXT                 -- опционально, поле в UI при сохранении
)
```

В UI раздела «История» — список изменений с фильтром по дате/автору/ключу, возможность развернуть diff и кнопка «Восстановить эту версию» (копирует значения в `config_active`, требует рестарта).

### 15.4. Безопасность раздела

- Раздел «Конфигурация» доступен только админам (на MVP — базовая авторизация, в `.env` пара логин/пароль).
- Все изменения пишутся в `config_history` с указанием автора.
- Изменения, которые могут привести к неработоспособности (выбор отсутствующей модели, нулевые пороги, пустой webhook URL), валидируются перед сохранением.

## 16. Тестовый чат

API + минимальный SPA в составе проекта.

**Функционал**:
- Поле ввода/выбора `user_id` (выпадающий список тестовых пользователей из генератора).
- Список сессий пользователя с возможностью удалить сессию.

**Авторизация и identity**: тестовый чат закрыт админской Basic Auth (см. раздел 1.1). `user_id` в запросах — это **impersonation для дебага**: разработчик авторизован как админ, но шлёт запросы «от имени» выбранного тестового пользователя. Это сознательное расхождение с боевым чатом, где identity берётся из токена и подмена `user_id` запрещена. В prod-пресете тестовый чат либо отключён, либо доступен только из доверенной сети.

## 17. Локализация и источник текстов

- На MVP — только русский. Архитектура поддерживает мультиязычность с самого начала.
- Локаль выбирается из профиля пользователя (`language`), фоллбэк — `ru`.

**Граница «что где лежит»**:

| Категория текстов | Где хранится | Кто редактирует |
|---|---|---|
| Системные промпты LLM (для каждого этапа pipeline) | `/i18n/{locale}/prompts/...` | разработчик, через PR |
| Шаблоны безопасных отказов (blocked-ветка) | `/i18n/{locale}/refusals/...` | разработчик |
| Формулировки уточняющих вопросов | `/i18n/{locale}/clarifications/...` | разработчик |
| Реестр шаблонных сценариев (декларации шагов) | `/i18n/{locale}/templates/...` или код | разработчик |
| `product_faq.answer` (ответы на «как добавить тренировку») | БД | продакт через админку |
| Описания и пояснения к алертам (что увидит пользователь) | БД | продакт через админку |
| Имена и описания tools (для tool retrieval) | код / `/i18n/{locale}/tools/...` | разработчик |

**Принцип**: тексты, отражающие **поведение Агента**, — в i18n (версионирование, ревью, тесты). Тексты, которые **редактируются продактом без деплоя**, — в БД (`product_faq`, пояснения к алертам). Hardcoded строк, видимых пользователю, в Python-коде нет.

Реестр промптов (`system_prompt_id`, см. раздел 15.2.B) — часть `/i18n/{locale}/prompts/`.

## 19. Docker Compose: пресеты dev и prod

### 19.1. Общая идея

Два пресета через стандартный паттерн override:

- `docker-compose.yml` — базовая конфигурация, общая для обоих пресетов.
- `docker-compose.dev.yml` — override для разработки.
- `docker-compose.prod.yml` — override для продакшна.

**Команды запуска**:
```bash
# dev
docker compose -f docker-compose.yml -f docker-compose.dev.yml --env-file .env.dev up

# prod
docker compose -f docker-compose.yml -f docker-compose.prod.yml --env-file .env.prod up -d
```

Удобно завернуть в `Makefile` (`make dev`, `make prod`, `make restart-agent`, `make logs`).

### 19.2. Хранение данных

Все стейтфул-данные монтируются в папку `data/` в корне проекта через `volumes:`. Раскладка:

```
data/
  postgres/        # PostgreSQL data
  redis/           # Redis dump/aof
  rag_index/       # артефакты индексации, если что-то лежит вне Postgres
  uploads/         # загруженные методики тренеров (на будущее)
```

Папка `data/` — в `.gitignore`. Одинаковая раскладка в dev и prod.

**LLM-бэкенды в этой раскладке не участвуют** — они вне scope проекта, см. 19.3.

### 19.3. LLM-бэкенды (вне scope проекта)

**Ollama, vLLM, TEI/Infinity не входят в docker-compose этого проекта** — ни в dev, ни в prod. Предполагается, что они подняты отдельно (отдельным docker-compose, systemd-сервисом, на той же машине или на соседней) и доступны по сети. Их установка, настройка, выбор моделей и поддержка — задача инфраструктурного слоя, не Агента.

Агент общается с ними через `LLMClient` и `EmbeddingsClient`, конфигурация — через `LLM_BASE_URL` и `EMBEDDINGS_BASE_URL` в `.env` (см. раздел 18) и потом через раздел «Конфигурация» (см. раздел 15).

**Сетевая доступность из контейнера Агента**:
- Если бэкенды на той же хост-машине — добавить в compose `extra_hosts: ["host.docker.internal:host-gateway"]` и в `.env` указать `LLM_BASE_URL=http://host.docker.internal:11434` и аналогично для embeddings. Это работает одинаково в dev и prod на Linux; на Mac/Windows `host.docker.internal` доступен из коробки.
- Если бэкенды на соседней машине — обычный URL по IP/DNS.
- Если бэкенды в соседней docker-сети на той же машине — подключить эту сеть как `external` в compose Агента.

**Что зафиксировано из коробки в .env**:
- `.env.dev`: `LLM_BACKEND=ollama`, URL по умолчанию указывает на `host.docker.internal:11434`.
- `.env.prod`: `LLM_BACKEND=vllm`, URL заполняется при разворачивании под конкретную инфраструктуру.

Health-check в админке (раздел 14, Dashboard) пингует эти URL и показывает доступность — это единственный способ Агента узнать, что бэкенды живы.

### 19.4. Сервисы и порты

В compose-файлах проекта поднимаются только сервисы, которые относятся к Агенту:

| Сервис | base | dev | prod |
|---|---|---|---|
| `agent` (FastAPI) | внутри сети | порт наружу для отладки + volume кода | порт за reverse-proxy (nginx/traefik), без volume кода |
| `postgres` | внутри сети | порт `5432` наружу для DBeaver | только внутри сети |
| `redis` | внутри сети | порт `6379` наружу для redis-cli | только внутри сети |

В dev порты Postgres и Redis открыты на хост — для прямого подключения дебаггерами и админ-инструментами.

LLM-бэкенды (Ollama, vLLM, TEI/Infinity) — **вне** этого compose, см. 19.3.

### 19.5. Применение изменений в dev

**Hot-reload не используется.** Изменения в коде применяются ручным перезапуском контейнера Агента **без пересборки**:

```bash
docker compose restart agent
```

Чтобы это работало, **в dev-пресете папка с кодом смонтирована в контейнер как volume** (`./app:/app/app:ro` или аналогично). Это позволяет применить изменения за секунды, без `docker build`.

Пересборка нужна только при изменении:
- зависимостей (`requirements.txt` / `pyproject.toml`),
- `Dockerfile`,
- системных пакетов внутри образа.

В prod **volume кода не пробрасывается** — код запекается в образ при сборке.

### 19.6. Применение изменений конфига

Hot-reload кода (если бы он был включён) **не должен** считаться применением изменений в `config_active`. Конфиг читается из БД при старте процесса Агента и фиксируется на время его жизни. Чтобы новый конфиг вступил в силу, нужен явный рестарт контейнера (см. раздел 15.1).

В dev это значит то же самое: после изменения конфига в админке — `docker compose restart agent`.

### 19.7. Различия dev vs prod (сводно)

Что **одинаково**:
- Версии Postgres и Redis.
- Миграции и схема БД.
- Структура `data/`.
- Схема логирования.
- Способ обращения к LLM/embeddings — через `LLMClient` / `EmbeddingsClient`, бэкенды одинаково внешние.

Что **отличается**:
- URL бэкендов (`LLM_BASE_URL`, `EMBEDDINGS_BASE_URL`) — разные для dev и prod.
- Тип бэкенда: обычно Ollama в dev, vLLM/TEI в prod (но это конфиг, а не структура compose).
- Volume кода: только dev.
- Открытые порты БД на хост: только dev.
- Reverse-proxy перед Агентом: только prod.
- Лимиты ресурсов (`deploy.resources.limits`): только prod.
- Уровень логов: `DEBUG` в dev, `INFO` в prod.
- Restart policy: `no` в dev, `unless-stopped` в prod.

## 20. Стиль кода и комментариев

**Язык** — простой английский. Короткие фразы, обычные слова, без формального тона и «корпоративных» оборотов.

**Принцип**: комментарий имеет право на жизнь только если в нём есть смысл, не виден из кода.

**Что писать**:
- неочевидное «почему»,
- скрытые инварианты,
- обходы конкретных багов,
- тонкости поведения, которые удивят читателя.

**Что НЕ писать**:
- пересказ имён и сигнатуры (`# increment counter`, `# returns user`),
- ссылки на текущую задачу/issue/автора (`# added for #42`, `# fix from PR`),
- TODO без конкретики,
- многоабзацные docstrings там, где хватает одной строки.

**Docstrings** — одна короткая строка по делу. Развёрнутый блок — только если у функции реально нетривиальный контракт (edge cases, инварианты входа/выхода).

## 21. Что Агент должен уметь (acceptance criteria)

1. Точно и быстро отвечать на конкретные вопросы по данным пользователя:
   - детальное представление: «Мои пробежки сегодня», «Мои шаги за неделю по дням»;
   - суммированное: «Мои пробежки за месяц», «Мой рекорд по шагам и калориям за всё время».
2. Простые ответы («Сколько шагов я прошёл сегодня») не сухие — содержат полезную аналитику: % от базы, сравнение с нормой по профилю.
3. Корректно отвечать на сложно составленные профильные вопросы.
4. Отвечать на справочные и профильные вопросы через RAG (профильные) и `product_faq` (про продукт).
5. Стабильно отвечать на шаблонные вопросы вроде «Утренний анализ» — без лишних раздумий и LLM-итераций сверх плана шаблона.
6. Помнить прошлые вопросы и ответы в рамках диалога (10 пар + summary).
7. Точно определять нехватку данных и сообщать об этом, а не выдумывать числа.
8. Давать рекомендации и строить планы тренировок, опираясь на RAG и данные пользователя.
9. Уметь задавать уточняющие вопросы и корректно учитывать ответ.
10. Поддерживать простой смолток, не уходя далеко от профиля.
11. Не отвечать на опасные и сильно вне-профильные вопросы — мягкий отказ из шаблона.
12. Никогда не считать числа сама — все агрегаты приходят из tools.

## 22. Этапы (примерная декомпозиция)

1. **Каркас**: репо, два compose-пресета (dev/prod), `data/` структура, FastAPI-скелет, Postgres+pgvector, Redis, миграции, health-чеки, seed-логика `.env → config_active`.
2. **Данные**: ORM, репозитории, детерминированный генератор тестовых данных с 4 персонами.
3. **LLM/Embeddings clients**: интерфейсы и обе реализации, прогон против внешнего Ollama (поднятого вне проекта).
4. **Tools-каркас**: реестр, схемы, базовый набор tools на пользовательских данных, tool retrieval.
5. **RAG**: чанкинг, индексация, retrieval с фильтром по collection, демо-набор знаний.
6. **Pipeline**: Context Builder → Intent → Router (все 5 веток) → Response Generator → SSE delivery.
7. **Шаблоны**: реестр шаблонов + `morning_analysis` и `weekly_summary`.
8. **Безопасность**: classifier + blocked-ветка + шаблоны отказов.
9. **Память диалога**: Redis-сессии, rolling summary.
10. **Логирование**: все таблицы, партиционирование, retention через DROP PARTITION, daily_stats.
11. **Админка** (часть 1): API + SPA — Dashboard, Логи, Сессия.
12. **Админка** (часть 2): раздел «Конфигурация» — все подразделы (модели, пресеты по этапам, пороги, RAG, product_faq, шаблоны, алерты, безопасность), `config_history`, валидация, баннер про рестарт.
13. **Тестовый чат**: API + минимальный SPA.
14. **Proactive alerts**: каркас + правило `hrv_drop` + webhook.
15. **i18n**: вынос всех текстов и промптов, ru-локаль.
16. **Тесты**: unit на tools, интеграционные на pipeline по детерминированным данным.
